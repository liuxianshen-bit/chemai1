## Context

Phase 1 修好底盘，Phase 2 打通页面。现在 agent 需要能处理"准备期中考试"这类需要跨多个知识点、多个 skill 的复杂教学任务。当前执行方式（LLM 每轮 think 一次猜一步）缺乏全局视角，容易遗漏步骤或重复执行。

## Goals / Non-Goals

**Goals:**
- LLM 驱动的目标拆解：复杂教学意图 → 结构化步骤 DAG
- 按计划逐步执行 + 观察 → 必要时 replan
- 前端实时展示计划执行进度

**Non-Goals:**
- 不支持并行步骤执行（Phase 3 只做串行，并行放到后续）
- 不引入外部规划框架
- 不改动 skill 实现

## Decisions

### D1: 规划触发 — keyword 启发式 vs LLM 判断

**选择**: keyword 启发式 `_needs_planning()`（命中 2+ 个规划关键词才激活）。

**理由**: 省掉一次 LLM 调用。分类器（Phase 2）已经做了一次 LLM 调用做意图识别，再加一次"是否需要规划"的判断就两次了。关键词启发式 >90% 准确率，边缘 case（误触发/漏触发）容忍度高——误触发只会多展示一个单步计划卡片，漏触发只是降级为普通多步执行。

### D2: 执行路径 — 独立方法 vs 修改现有 run_stream

**选择**: 新增 `run_with_plan_stream()` 方法。

**理由**: 保持现有路径不变（简单对话走现有的 `run_stream`，复杂目标走 `run_with_plan_stream`）。两个方法可以独立测试和调试。未来如果效果稳定，可以合并。

### D3: 依赖注入 — 简单模板 vs 表达式语言

**选择**: Regex 模板 `${step_N.field}`。

**理由**: 实际场景中依赖关系很简单（"步骤 3 的出题范围需要步骤 1 和步骤 2 的搜索结果"），不需要表达式语言。regex 替换零延迟、零错误。

### D4: Replan 策略 — 固定上限 2 次

**选择**: 失败后重新规划最多 2 次。

**理由**: 避免无限规划循环。超过 2 次 replan → 跳过剩余步骤 → 输出已完成的部分结果 + 失败说明。

## Risks / Trade-offs

- **规划 LLM 调用增加延迟**: generate plan ~1.5s。对于"准备考试"这类操作，用户预期等待时间本来就长（agent 要做多步工作），可接受。
- **Keyword 启发式漏触发**: 如果用户说"帮我整理一下这学期的重点内容"但没命中关键词 → 降级为普通多步执行，功能不损失。
- **Plan 步骤数 >6 被截断**: LLM prompt 限制 max 6 步。超过 6 步的场景极少，且可通过多次对话完成。
